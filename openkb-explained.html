#1 The Big Picture

OpenKB has a fundamentally different approach from traditional RAG (Retrieval-Augmented Generation). Instead of re-deriving knowledge from scratch on every query, it compiles documents into a persistent, interlinked wiki — then queries that wiki.

Traditional RAGOpenKB
Knowledge Re-derived per query from chunks Compiled once into persistent wiki pages
Retrieval Vector similarity (embedding-based) Vectorless — PageIndex tree + LLM reasoning
Cross-document No synthesis; chunks are isolated Concept/entity pages link across documents
Accumulation Nothing compounds Each new doc enriches existing concepts
Long documents Chunked, loses structure Full hierarchical tree preserved via PageIndex

#2 PageIndex — Vectorless Tree Indexing

PageIndex is the core innovation that lets OpenKB handle long documents without vector databases. Instead of chunking a document into flat embedding vectors, PageIndex builds a hierarchical summary tree that preserves the document's logical structure.

KEY INSIGHT Why Trees Beat Vectors for Long Documents

A 200-page PDF has complex internal structure — chapters, sections, subsections, figures. Vector embeddings flatten this into 512-dimensional points, losing all structural relationships. PageIndex preserves the hierarchy: the LLM can navigate from the table of contents down to the exact page range it needs, just like a human would.

How PageIndex Builds the Tree

1
PDF Ingestion & Page Extraction
The PDF is processed page-by-page. Each page's text content is extracted (via OCR for scanned docs in cloud mode, or pymupdf locally). Images and figures are also extracted and stored separately under wiki/sources/images/. The raw page content is saved as a JSON array in wiki/sources/{doc_name}.json, where each entry has {"page": N, "content": "...", "images": [...]}.
2
LLM-Powered Structure Detection
The PageIndex client sends the document to the configured LLM (e.g., GPT-4) which analyzes the document's logical structure — detecting chapters, sections, subsections — and builds a hierarchical tree. Each node gets: a title, start/end page indices, a summary of that section's content, and optional child nodes. This is the "reasoning-based" part — the LLM uses its understanding of the document rather than statistical similarity.
# IndexConfig controls what the tree contains: IndexConfig( if_add_node_text=True, # Include node text excerpts if_add_node_summary=True, # LLM-generated section summaries if_add_doc_description=True, # Overall document description )
3
Tree Structure Output
The result is a JSON tree with doc_name, doc_description, and a recursive structure array. This tree is rendered into a Markdown summary page at wiki/summaries/{doc_name}.md — each node becomes a heading with its page range and summary text. The frontmatter includes doc_type: pageindex and a full_text: sources/{doc_name}.json pointer for deep retrieval.
4
Crash-Safe Persistence
All writes go through OpenKB's mutation system (mutation.py). Before any write, a MutationSnapshot backs up affected paths. Writes are journaled. If anything fails, the journal triggers an automatic rollback — restoring the KB to its pre-mutation state. This means openkb add is transactional: it either fully succeeds or cleanly rolls back. The PageIndex blob store (under .openkb/files/) is tracked via snapshot.track_new() so orphaned blobs are cleaned up on failure.

#3 The LLM Compiler Pipeline

After PageIndex creates the summary tree for long documents (or the converter extracts markdown for short docs), the compiler (agent/compiler.py) runs a 5-step LLM pipeline that turns raw content into interlinked wiki pages.

Prompt Caching Optimization: The pipeline is designed to exploit Anthropic's prompt caching. The base context (schema + document content) is marked with cache_control: ephemeral and reused across all N+M+2 LLM calls for a single document. This dramatically reduces cost and latency when generating many concept/entity pages from the same document.

The 5 Steps (click each to expand)

1
Build Base Context CACHED
The system prompt is built from the wiki schema (AGENTS.md) and language setting. The full document content is attached as the user message with a cache_control breakpoint. This base context (system + document) is shared across ALL subsequent LLM calls for this document — the first call pays the input cost, subsequent calls hit the cache.
# System message built from schema: "You are OpenKB's wiki compilation agent... {schema_md} Write all content in {language} language. Use [[wikilinks]] to connect related pages." # User message with document content (cache breakpoint here): "New document: {doc_name} Full text: {content}" ← cache_control: ephemeral
2
Generate Summary
The LLM produces a JSON response with a description (one-liner under 100 chars) and content (full Markdown summary). The summary captures key concepts and findings, with [[wikilinks]] to potential concept pages. For long (PageIndex) documents, the prompt is adapted to work with the tree structure instead of raw text.
// LLM returns: { "description": "Introduces the Transformer architecture using self-attention", "content": "# Attention Is All You Need\n\nThis paper introduces the **Transformer**,\na sequence transduction model based entirely on [[concepts/attention]]..." }
3
Plan Concepts & Entities
With the summary in context, the LLM sees all existing concept and entity pages (as one-line briefs) and decides what to create, update, or cross-link. The plan separates concepts (abstract ideas) from entities (named things). Rules prevent duplication: "update" is preferred over "create" for existing topics.
// LLM plans wiki updates: { "concepts": { "create": [ {"name": "self-attention", "title": "Self-Attention Mechanism"}, {"name": "transformer", "title": "Transformer Architecture"} ], "update": [{"name": "sequence-modeling", "title": "Sequence Modeling"}], "related": ["neural-networks"] }, "entities": { "create": [ {"name": "google-brain", "title": "Google Brain", "type": "organization"} ], "update": [], "related": [] } }
4
Generate Pages CONCURRENT
All new and updated concept/entity pages are generated concurrently via asyncio.gather. Each page gets its own LLM call, but they all share the cached base context (system + document + summary). New pages get the "write" prompt; updated pages get the "rewrite" prompt that includes the existing page content so the LLM integrates rather than replaces. Entity pages also specify a type field (person, organization, etc.).
Wikilink Whitelist: Before page generation, the compiler sends a message listing ALL valid wikilink targets. The LLM must only use [[links]] to targets in this whitelist — preventing broken links and ghost references. Any concept not yet in the wiki must be written as plain text.
5
Cross-link & Update Index
After all pages are generated, code (not LLM) adds [[wikilinks]] from existing concept pages to the new summary, and updates related concept pages with cross-references. The summary itself gets a final LLM rewrite pass to ensure all links match the now-known wikilink whitelist. Finally, index.md is updated with entries for all new/modified pages. The frontmatter on each page is managed by code — never by the LLM.
# Frontmatter is code-managed (OKF format): --- type: Concept description: The core attention mechanism enabling parallel sequence processing sources: - attention-is-all-you-need --- # Cross-ref backlinks are appended by code: ## Related Documents - [[summaries/attention-is-all-you-need]]

#4 Query & Retrieval — Reasoning, Not Vectors

When you run openkb query or openkb chat, the system uses an agentic retrieval strategy. The LLM agent reads the wiki like a researcher would — starting from the index, drilling into summaries, then fetching specific page ranges from source documents when needed.

AGENT TOOLS The Query Agent's Toolkit
read_file(path)
Read any wiki .md file — index, summaries, concepts, entities.
get_page_content(doc, pages)
Fetch specific pages from a PageIndex long doc's JSON source.
get_image(path)
View extracted figures/charts as base64 images.
write_file(path, content)
Save explorations/analyses to wiki/explorations/.

The Retrieval Strategy (from the agent's instructions)

1
Read index.md — see all docs, concepts, entities
The index gives a bird's-eye view: every document with its one-liner description, marked as (short) or (pageindex) to indicate type. The agent decides which summaries and concept pages are relevant to the question.
2
Read relevant summaries & concept pages
Summary pages provide the compiled understanding of each document. Concept pages provide cross-document synthesis. For "who/what is X" questions, entity pages are checked first — they're the fastest path to factual answers.
3
Drill into source content when summaries aren't enough
Each summary's full_text frontmatter points to the source. For short docs: read_file("sources/doc.md"). For PageIndex docs: get_page_content("doc", "3-5,12") — the agent uses the tree structure in the summary to target specific page ranges rather than fetching the whole document. This is the "reasoning-based retrieval" — the agent reads the tree, reasons about which sections are relevant, and fetches only those.
4
Synthesize answer grounded in wiki content
The agent produces a clear, concise answer citing specific wiki content. Before each tool call, it outputs a short sentence explaining its reasoning — making the retrieval process transparent and debuggable.
Why this works better than vector search: The agent uses semantic understanding to navigate the document tree — it knows that "methods" are in section 3 and "results" in section 5. Vector search would return the top-K chunks by cosine similarity, potentially missing relevant content that uses different vocabulary but is structurally adjacent.

#5 Walkthrough: Adding "Attention Is All You Need"

📝
Scenario: You add the famous Transformer paper to your KB.
Let's trace exactly what happens at each step.
STEP 1 You run the command
$ openkb add attention-is-all-you-need.pdf

The CLI detects this is a PDF and routes to the long-document pipeline (PageIndex).

STEP 2 Crash-safe mutation begins

Before any write, mutation.snapshot_paths() backs up every file that will be touched:

# Snapshot targets: wiki/index.md # Will be updated with new entries wiki/summaries/ # New summary page will be created wiki/concepts/ # New concept pages will be created wiki/entities/ # New entity pages will be created wiki/sources/ # Source content will be written .openkb/hashes.json # Registry of ingested docs # A journal file is written: .openkb/journal/a1b2c3d4.json → {"status": "active", "operation": "add", ...}

If anything fails from here on, the journal triggers automatic rollback.

STEP 3 PageIndex builds the tree

The PageIndexClient sends the PDF to the LLM for structural analysis:

# The LLM analyzes the 15-page paper and produces: { "doc_name": "Attention Is All You Need", "doc_description": "Proposes the Transformer, a novel architecture based entirely on attention mechanisms", "structure": [ { "title": "Abstract", "start_index": 1, "end_index": 1, "summary": "Proposes Transformer model achieving 28.4 BLEU on EN-DE translation..." }, { "title": "Introduction", "start_index": 1, "end_index": 2, "summary": "Motivates moving beyond recurrent models to pure attention..." }, { "title": "Model Architecture", "start_index": 2, "end_index": 5, "summary": "Encoder-decoder with stacked self-attention and feed-forward layers...", "nodes": [ {"title": "Scaled Dot-Product Attention", "start_index": 3, "end_index": 4, "summary": "..."}, {"title": "Multi-Head Attention", "start_index": 4, "end_index": 4, "summary": "..."}, {"title": "Positional Encoding", "start_index": 5, "end_index": 5, "summary": "..."} ] }, // ... Experiments, Results, Conclusion ] }

Simultaneously, the PDF pages are extracted and saved:

# wiki/sources/attention-is-all-you-need.json [ {"page": 1, "content": "Attention Is All You Need\n\nAshish Vaswani...", "images": []}, {"page": 2, "content": "recurrent models typically factor computation...", "images": []}, {"page": 3, "content": "An attention function can be described as...", "images": [{"path": "sources/images/attention-is-all-you-need/p3_img1.png"}]}, // ... pages 4-15 ]
STEP 4 LLM Compiler — 5-step pipeline

Step 4a: Summary Generation

The LLM reads the PageIndex tree summary and produces a wiki summary page:

# LLM output (JSON): { "description": "Introduces the Transformer architecture using self-attention", "content": "# Attention Is All You Need\n\nThis paper introduces the **Transformer**,\na novel architecture based entirely on [[concepts/self-attention]] mechanisms,\ndispensing with recurrence and convolutions entirely.\n\n## Key Contributions\n- **Self-attention** as the sole mechanism for computing representations\n- **Multi-head attention** allowing the model to attend to information\n from different representation subspaces\n- Achieved **28.4 BLEU** on WMT 2014 English-to-German translation\n..." }

Step 4b: Concept & Entity Planning

The LLM sees existing concepts (if any) and plans what to create/update:

# Existing concepts: (none yet) ← first document in KB # Existing entities: (none yet) # LLM plan output: { "concepts": { "create": [ {"name": "self-attention", "title": "Self-Attention Mechanism"}, {"name": "transformer", "title": "Transformer Architecture"} ], "update": [], "related": [] }, "entities": { "create": [ {"name": "google-brain", "title": "Google Brain", "type": "organization"}, {"name": "ashish-vaswani", "title": "Ashish Vaswani", "type": "person"} ], "update": [], "related": [] } }

Step 4c: Concurrent Page Generation

All 4 pages (2 concepts + 2 entities) are generated simultaneously via asyncio.gather:

self-attention
concept / create
transformer
concept / create
google-brain
entity / create
ashish-vaswani
entity / create

All 4 LLM calls share the cached base context — only the page-specific prompt is new.

Step 4d: Cross-linking & Index Update

Code (not LLM) adds backlinks and updates the index:

# index.md gets updated: ## Documents - [[summaries/attention-is-all-you-need]] — Introduces the Transformer architecture using self-attention (pageindex) ## Concepts - [[concepts/self-attention]] — The core attention mechanism enabling parallel sequence processing - [[concepts/transformer]] — Neural network architecture based entirely on attention mechanisms ## Entities - [[entities/google-brain]] (organization) — AI research lab at Google behind the Transformer - [[entities/ashish-vaswani]] (person) — Lead author of "Attention Is All You Need"
STEP 5 The compiled wiki

Browse the resulting wiki pages:

summaries/attention-is-all-you-need.md
concepts/self-attention.md
concepts/transformer.md
entities/google-brain.md
index.md
STEP 6 Querying the wiki
$ openkb query "How does multi-head attention work?"

The query agent's reasoning trace:

# Agent reasoning: 1. Reading index.md to find relevant documents and concepts. → read_file("index.md") 2. The concept "self-attention" looks relevant. Reading it. → read_file("concepts/self-attention.md") 3. The summary mentions multi-head attention on pages 4-5. Let me check the source. → get_page_content("attention-is-all-you-need", "4-5") 4. There's a figure on page 3 showing the architecture. Let me view it. → get_image("sources/images/attention-is-all-you-need/p3_img1.png") 5. Synthesizing answer from wiki content...
Notice: The agent navigated the tree structure — it read the summary, saw that "Model Architecture" covers pages 2-5, and targeted exactly pages 4-5 for multi-head attention details. No vector search needed. It also pulled the architecture diagram. This is reasoning-based retrieval.
BONUS What happens when you add a second paper?

When you add "BERT: Pre-training of Deep Bidirectional Transformers", the compiler sees existing concepts and updates them instead of creating duplicates:

# The LLM plan now shows: { "concepts": { "create": [ {"name": "pre-training", "title": "Pre-training in NLP"} ], "update": [ {"name": "self-attention", "title": "Self-Attention Mechanism"}, ← UPDATE, not create! {"name": "transformer", "title": "Transformer Architecture"} ← UPDATE, not create! ], "related": [] }, ... }

The existing concept pages are rewritten to integrate BERT's perspective — the "self-attention" page now covers both the original Transformer and BERT's bidirectional variant. Knowledge compounds.
