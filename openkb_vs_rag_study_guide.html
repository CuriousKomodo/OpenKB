The LLM Compiler

OpenKB's compiler is the heart of its ingestion pipeline. It runs every time you openkb add a document, transforming raw content into interconnected wiki pages through a multi-step LLM pipeline.

Click each step to expand its details, or use the controls below to walk through the pipeline.

1
Build Base Context Code
Assemble system prompt + document content into the shared message prefix.

The compiler builds a base context that will be reused (and cached) across all subsequent LLM calls:

  • System prompt: loaded from wiki/AGENTS.md — the wiki schema, conventions, and language setting.
  • Document content:
    • Short docs (<20 pages): full Markdown text (converted via markitdown).
    • Long PDFs (≥20 pages): the PageIndex tree summary (hierarchical structure with node summaries, descriptions, and page ranges).

This context is tagged with Anthropic cache_control markers so that providers that support prompt caching (Anthropic, OpenRouter→Claude) can cache it across all N subsequent calls. For other providers, the markers are stripped automatically.

2
Generate Summary LLM Call #1
LLM reads the document and produces a structured summary page.

The full document content is sent to the LLM with a prompt requesting a JSON response with two keys:

{ "description": "Single sentence, <100 chars, main contribution", "content": "Full summary in Markdown with [[wikilinks]]..." }
  • The summary must include key concepts, findings, ideas, and [[wikilinks]] to concepts that could become cross-document concept pages.
  • For long docs, the LLM reads the PageIndex tree summary (not the raw PDF) and writes a concise overview that captures key themes.
  • Output is written to wiki/summaries/<doc_name>.md with YAML frontmatter (type, description, doc_type, full_text path).
3
Concepts & Entities Plan LLM Call #2
LLM decides which concept and entity pages to create, update, or cross-link.

The LLM receives the summary it just wrote plus a compact listing of all existing concepts (from concepts/*.md frontmatter) and entities (from entities/*.md with source counts). It returns a plan:

{ "concepts": { "create": [{ "name": "attention-mechanisms", "title": "Attention Mechanisms" }], "update": [{ "name": "transformer-architecture", "title": "Transformer Architecture" }], "related": ["neural-networks", "sequence-modeling"] }, "entities": { "create": [{ "name": "anthropic", "title": "Anthropic", "type": "organization" }], "update": [...], "related": [...] } }

Key rules enforced by the prompt:

  • Update over create: if a concept/entity already exists, prefer "update" to avoid duplicates.
  • Concepts vs entities: a concept is an abstract idea (e.g. "agentic systems"); an entity is a named thing (e.g. "Anthropic"). They cross-link but never merge.
  • Entity gating: only create entity pages for things central to the doc or likely to recur. ~5-15 entities per doc is typical; passing mentions are skipped.
  • Conservative start: for the first few documents, only 2-3 foundational concepts are created.
  • Entity types are configurable per-KB via .openkb/config.yaml (default: person, organization, place, product, other).
4
Generate / Rewrite Pages LLM Calls #3-N (concurrent)
All new and updated concept/entity pages are generated concurrently via async LLM calls.

This is where the bulk of LLM cost lives. The plan from Step 3 drives concurrent async calls — one per page to create or update:

  • New concept page: LLM writes a full concept page from scratch — explanation, key details from the source, and [[wikilinks]] to related concepts and the summary.
  • Updated concept page: LLM receives the existing page content and rewrites the full page integrating new information naturally (not just appending). Preserves existing structure and intent.
  • New entity page: same as concept but includes a type field (person, organization, place, product).
  • Updated entity page: same rewrite pattern — full page rewrite with new facts integrated.

Safety mechanisms:

  • Truncation protection: if any call hits the token limit, the page is skipped entirely rather than writing partial content.
  • Wikilink whitelist: before these calls, the LLM receives a whitelist of all valid wiki page targets. It may only link to pages that actually exist — no invented links.
  • JSON repair: malformed LLM JSON output is automatically repaired via json_repair; if it's still unparseable, the raw text is treated as prose Markdown.

Prompt Caching Optimization

The pipeline is designed around two cache breakpoints:

System + Doc Cached across ALL calls
+ Summary Cached across concept/entity calls
+ Per-page prompt Unique per call

The expensive document content is sent to the API once and reused for every subsequent call via Anthropic's prompt caching. This dramatically reduces both cost and latency for the concurrent calls.

5
Post-Processing Code + LLM
Cross-references, wikilink validation, index updates, and summary rewrite.

A mix of deterministic code and one final LLM call to finalize everything:

  • Cross-reference links Code — "related" concepts/entities from the plan get [[wikilinks]] added to their existing pages without rewriting content. Lightweight linking only.
  • Wikilink validation Code — all [[wikilinks]] in generated pages are checked against actual wiki pages. Invalid/dangling links are stripped by strip_ghost_wikilinks().
  • Index update Code — wiki/index.md is updated with new entries under its ## Documents, ## Concepts, and ## Entities sections. Entries include the description from each page's frontmatter.
  • Summary rewrite LLM — one final LLM call rewrites the summary to upgrade plain-text mentions to [[wikilinks]] where concept pages now exist, while preserving all factual content.
  • Frontmatter management Code — each page gets YAML frontmatter tracking type, description, sources (which docs contributed), and doc_type. On updates, the new source is prepended to the sources list.

All file writes use atomic write (openkb/locks.py): temp file + os.replace, so a crash mid-write never leaves a corrupted page on disk.

Total Cost Profile

A single openkb add paper.pdf typically triggers:

Step 2: Summary generation1 LLM call
Step 3: Concepts/entities plan1 LLM call
Step 4: Page generation (concurrent)5-15 LLM calls
Step 5: Summary rewrite1 LLM call

Total: ~8-18 LLM calls per document. Step 4 dominates cost but benefits most from prompt caching.

Deep Dive

Expand each topic to study the details.

OpenKB Ingestion

  • Short docs (<20 pages): converted to Markdown via markitdown, then read in full by the LLM.
  • Long PDFs (≥20 pages): processed by PageIndex into a hierarchical tree index with node summaries and descriptions. Multiple LLM calls per document.
  • The LLM compiler then generates: a summary page, creates/updates concept pages, extracts entity pages, and writes cross-links.
  • A single source can touch 10-15 wiki pages. Each new document is reconciled against all existing concepts — cost grows superlinearly.

RAG Ingestion

  • Documents are split into chunks (fixed-size, sentence-based, or semantic).
  • Each chunk is embedded using an embedding model (e.g., text-embedding-3-large). ~100x cheaper per token than generation.
  • Embeddings are stored in a vector database (Pinecone, Weaviate, Chroma, etc.).
  • Cost grows linearly — no cross-document reconciliation at ingest time.
  • Optional: generate summaries per chunk or per document for hierarchical retrieval (adds LLM cost).

OpenKB: Agent-Driven Navigation

  • An LLM agent is given tools: read_file, get_page_content, get_image.
  • The agent reads index.md to see all documents and concepts with brief summaries.
  • It decides which summary, concept, or entity pages to read — then optionally drills into source pages.
  • Each decision is an LLM inference call. Up to 50 turns allowed. Typical queries use 3-10 tool calls.
  • This is reasoning-based retrieval: the LLM understands document structure and navigates intelligently.

RAG: Vector Search + Reranking

  • Stage 1 — Retrieval: Query is embedded, ANN search returns top-k candidates (~100ms). Algorithms: HNSW, IVF, ScaNN.
  • Stage 2 — Reranking (optional):
    • Cross-encoder reranker (e.g., BGE-reranker, Cohere Rerank): scores each (query, chunk) pair. +0.5-2s.
    • LLM reranker: uses an LLM to score relevance. Most accurate but slowest. +2-5s.
  • Stage 3 — Generation: Top-k reranked chunks are stuffed into the LLM prompt as context.
  • Tunable parameters: chunk size, overlap, embedding model, k, reranker choice, number of reranked results.

Factual Lookup (single document)

Both perform well. RAG with a good cross-encoder reranker is very competitive. OpenKB's summary pages often contain the answer directly, avoiding source lookup.

Cross-Document Synthesis

OpenKB's biggest advantage. Concept pages already synthesize information across documents at compile time. The agent reads one page instead of stitching fragments. RAG must retrieve chunks from multiple documents and rely on the LLM to synthesize at query time — often missing relevant chunks.

Entity-Centric Queries

OpenKB maintains dedicated entity pages (people, orgs, places, products) that aggregate all mentions. RAG must hope that vector search finds all relevant chunks mentioning the entity — name variations and scattered references are problematic.

Long Document Deep Dive

OpenKB's PageIndex tree lets the agent target specific page ranges. RAG depends on chunk boundaries — poorly split chunks lose context. Hierarchical chunking helps but adds complexity.

Contradictions

OpenKB's LLM linter flags contradictions at compile time. RAG has no built-in mechanism — conflicting chunks may both be retrieved and presented to the user.

RAG accuracy is highly sensitive to parameter choices:

  • Chunk size: 256-2048 tokens typical. Smaller = more precise retrieval, larger = more context per chunk. No universally optimal value.
  • Chunk overlap: 10-25% prevents information loss at boundaries.
  • Embedding model: OpenAI text-embedding-3-large, Cohere embed-v4, BGE-M3, etc. Performance varies by domain.
  • Top-k: 3-20 chunks. More = higher recall, but more noise and cost.
  • Reranker: None → cross-encoder → LLM reranker. Each level adds latency but improves precision.
  • Indexing algorithm: HNSW (fast, memory-heavy), IVF (scalable, slightly less accurate), ScaNN (Google, good balance).
  • Hybrid search: Combining dense (vector) + sparse (BM25) retrieval often outperforms either alone.

OpenKB avoids this parameter space entirely by using structured compilation — but introduces its own complexity (LLM prompt engineering for the compiler).

Choose OpenKB when:

  • You have a stable, curated corpus queried many times (the upfront cost amortizes).
  • Cross-document synthesis and entity tracking are important.
  • You need a persistent, browsable knowledge artifact (the wiki itself has value).
  • Knowledge quality matters more than speed.
  • Documents are long and complex (PageIndex tree indexing shines).

Choose RAG when:

  • Documents change frequently and you need fast re-indexing.
  • You need sub-second retrieval latency (user-facing search, chatbots).
  • The corpus is very large (10K+ documents).
  • Queries are mostly single-document factual lookups.
  • Budget is tight — embedding is orders of magnitude cheaper than LLM compilation.
